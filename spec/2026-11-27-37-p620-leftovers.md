# Spec: the cleanup-day procedure for the p620 RFactory pod leftovers

## Design

**This spec removes nothing.** It describes what happens on cleanup day: a go/no-go check, two owner OKs, a short list of removals by exact name, and the checks after. The day is **2026-12-01 or later**. Until then only read-only checks run.

The first slice is small on purpose: the tagged images, old web builds that can be proven, and the volume. Everything that the local pod (`deploy/pod.sh`) or the verify scripts still need stays. **No Keycloak change is made**, so no bus post is needed for one.

### 2. Order of the day

1. **Date and place.** `date -u +%F` prints `2026-12-01` or later, and `hostname` prints `p620`. Otherwise stop.
2. **Before-lists.** Save every podman image as full ID with its tags, and the names of all volumes, pods and secrets. Save the file names and modes in `~/.config/rfactory/`, `~/.config/rfactory-verify/` and `~/.local/share/rfactory/`. Names and modes only; no file is opened.
3. **Go/no-go check** (section 3). The result goes into #37 as one comment.
4. **First OK: the proof builds.** The owner reads the comment and allows the two builds of section 4. They are builds on p620, so they need this OK.
5. **Proof builds** (section 4), then the **removal list**: every item of section 5 with its exact name or full ID, the evidence for each untagged image, and which items the proofs ruled out. It goes into #37 as a second comment.
6. **Second OK: the removals.** The owner names the items. An approved intent, spec or plan is not this OK.
7. **Re-check, then remove** (section 5), in order, one command at a time. Just before the first removal, items 1 and 6 of the go/no-go are read again. Each command's result is one of `removed`, `kept`, `refused` or `failed`. A refusal or failure is never retried with force: the item stays. An unexpected change stops the day until the owner has seen it.
8. **After-checks** (Verification).
9. **Record** (section 6).

If any go/no-go item fails, steps 4 to 7 do not happen. The fallback stays and #37 gets a new date.

### 3. The go/no-go check

The agent's steps only read. The owner's test in item 2 is a real call: it uses the live deployment and writes a share record. Cluster names are #33's: context `k3d-factory`, namespace `factory`, Deployment `rfactory`, container `rfactory-web`, PVC `rfactory-data` mounted at `/var/lib/rfactory/actions` (`plan/2026-11-24-33-rfactory-in-cluster.md:62,80,290`). The Argo Application is `rfactory` in namespace `argocd` (read 2026-11-27: `Synced`, `Healthy`).

| # | Item | Who | Steps | Pass when |
|---|---|---|---|---|
| 1 | Healthy now | agent | `kubectl get` on the Deployment, its pod and the Application. | 1/1 available, 4/4 Ready, `Synced` and `Healthy`. The comment records the pod's UID and start time, the running image tags and digests, and the Application's revision: the check is for that revision. |
| 2 | Working now, from outside | owner | See 3.1. | A fresh sign-in reaches the page. The bot speaks a real answer about the board. The shared board appears in the call. |
| 3 | Stable over the week | agent, then owner | See 3.2. | Every pod replacement and restart the sources show has a known cause, and the owner attests the rest. |
| 4 | No open problem from the move | agent, then owner | `gh issue list --state open` in RFactory and in factory-gitops. The agent reads each open issue and says whether the move could be its cause, whatever words it uses. | The owner says none blocks. #67 does not (decision 2). The comment records the owner's judgement. |
| 5 | No record is lost | agent | See 3.3. | Every p620 file is in the PVC with the same SHA-256 sum, and a record written in the cluster before the running pod started is still there. |
| 6 | The fallback was not needed | owner | The owner confirms it. | The owner says the p620 pod was not started as a fallback since 2026-11-24. A start for development or verification does not count. That no pod `rfactory` exists and port 4180 is free only shows the state now. |

#### 3.1 The owner's test (item 2)

1. In a private browser window, sign in at `https://rfactory.freundcloud.org.uk`. The page shows the deployed commit (`GET /api/config`, `web/server.js:187`); the owner reads it out for the comment. An agent cannot: the route needs a signed-in member (`web/server.js:161-163`).
2. Start one call in `platform` (captions) mode, so #67 cannot cause a false failure.
3. Ask a question about the board that is not "stand up". A standup makes no AI call (`README.md:31`); a question goes to the brain (`web/call.js:268` with lookups on, `web/call.js:323` without).
4. Ask for the board to be shared and approve it. Then stop the share and end the call.

**Pass needs a real answer.** When the brain fails, the bot still speaks: "The model isn't available right now." or an apology (`web/call.js:280`). Those are a fail.

**What it proves:** the tunnel, Keycloak, the shared Claude login, the CFactory read key and the desktop runner. **What it does not:** the CFactory write key. A share reads the board with the read key (`web/server.js:342`); only an approved action uses the write key (`web/server.js:346-347`), and the test makes none. The comment says so.

#### 3.2 Stability (item 3)

Deploys replace the pod, so the restart counter starts again each time. The check reads:

- **The running pod:** `restartCount` and `lastState` of each of its four containers.
- **Every deploy:** the Deployment's ReplicaSets with their creation times, matched to the Application's sync history (`status.history`) or to factory-gitops commits. A ReplicaSet with no matching deploy is unexplained.
- **A replacement without a deploy:** the running pod's start time against its ReplicaSet's creation time. A pod much younger than its ReplicaSet was replaced for another reason (eviction, deletion, node restart), and needs a cause.
- **Known events:** the cluster restart on 2026-11-24 16:04 UTC, when `rfactory-web` exited once because CFactory was not up yet (`plan/2026-11-24-33-rfactory-in-cluster.md:359`). It is explained and does not fail the item.

**The limit:** crashes, failed starts and replacements inside an earlier ReplicaSet leave no trace in these sources, and old ReplicaSets are kept only up to the history limit. If the cluster keeps restart metrics, the plan adds that query (Open question 1). The owner attests everything the sources cannot show, and the comment says in plain words which part is attested.

#### 3.3 Records (item 5)

This is the last moment the comparison is possible.

- **p620 side:** `sha256sum` of every file in the volume, run with `podman unshare` over the volume's path, as #33 did (`plan/2026-11-24-33-rfactory-in-cluster.md:293`). The intent expects exactly `2026-11-17.jsonl` and `2026-11-19.jsonl`.
- **Cluster side:** one `kubectl exec` in the `rfactory-web` container: `find /var/lib/rfactory/actions -type f -exec sha256sum {} +`, with each file's size.
- **Rule 1:** every p620 file name is in the cluster list with the same sum. The cluster may hold more files. The app writes one file per day, `YYYY-MM-DD.jsonl`, and only appends to today's (`web/actions-record.js:9,17`), so a cluster record never changes a p620 file.
- **Rule 2:** a file dated 2026-11-24 or later, and dated before the running pod's start day, is in the PVC and is not empty. Only the cluster can have written it, and an earlier pod did. A share was approved from the cluster on 2026-11-24 (`plan/2026-11-24-33-rfactory-in-cluster.md:353`), so `2026-11-24.jsonl` is the expected one. The two copied p620 files do not count for this rule.

**The limits:** nobody holds a list of what the cluster should have written during the week. Rule 2 shows that cluster records outlive a pod replacement, not that none is missing or changed. Also, the app deletes record files older than 90 days (`web/actions-record.js:7,41-45`), so the cluster's copy of the p620 records goes in February 2027. The archive (R5) is the lasting copy.

### 4. The proof builds

**Web image.** `deploy/pod.sh:41` builds without `CHROME_VERSION`, so `web/Containerfile:7` pins `157.0.8103.78-1`. #33 recorded that this version no longer installs (`plan/2026-11-24-33-rfactory-in-cluster.md:35`); CI passes an empty value (`.github/workflows/deploy.yml:71-73`). Cached layers may hide that today.

The proof repeats `pod.sh`'s build from a clean, pushed checkout (`deploy/pod.sh:39-43`), with these changes:

- `--no-cache`, so the cache cannot hide a failure;
- `--pull=never`, so the base image in the shared store cannot move. Podman's default is `missing`, which would pull. If the base image is not there, the build fails and that is the result;
- `--layers=false`, so a failed build leaves no intermediate images behind;
- the tag `rfactory-web:rebuild-proof`, after `podman image exists` shows the tag is unused. The existing image is not touched.

Results:

- **It builds:** `pod.sh up` can rebuild the image. R2 and R4 may run.
- **It fails:** the web image stays, and so do the untagged web builds (R4): they may hold the only layers that still let a local build work. Follow-up issue B (section 6) covers the fix.

**STT image.** It comes from Nix (`deploy/pod.sh:114`, `deploy/images/default.nix:42-43`). The proof is that `nix build .#image-stt --no-link` succeeds on the same checkout. If it fails, the STT images stay. The proof does not load the archive into podman (`deploy/pod.sh:116-117`); that step needs no network and is left out so that the store does not change.

### 5. What is removed, and what stays

**Removed, in this order.** Every image removal is `podman rmi --no-prune <exact name or full ID>`. Without `--no-prune`, podman also removes parent images that become dangling, and those are not on the list. Just before each command, the name is resolved to its ID again and must equal the ID in the removal list.

| # | Item | Guard |
|---|---|---|
| R1 | `localhost/rfactory-spike:chrome`, `localhost/rfactory-spike:chromium` | None: `spike/run.sh:7` rebuilds them on every run. |
| R2 | `localhost/rfactory-web:latest`, then `localhost/rfactory-web:rebuild-proof` | Only if the web proof built. |
| R3 | `localhost/rfactory/stt:<tag>`, the three tags listed that day, one command per tag | Only if the Nix build succeeded. |
| R4 | Old web builds with no tag, one command per full ID | Only if the web proof built, and only the IDs the owner named. Proof below. |
| R5 | Volume `rfactory-actions`: archive first, then `podman volume rm rfactory-actions` | Item 5 passed, the archive is checked, and the volume's sums are read again and still equal it. No `-f`: podman refuses while a container uses the volume. |

The volume goes last, so that any surprise during the image removals happens while the local records are still there.

**R5, the archive.** `podman volume export rfactory-actions` into one tar file at the place the owner names (Open question 3). It is created with mode 600 from the start (`umask 077`) and never overwrites an existing file. It is good when it lists the same files and their sums equal the p620 sums of 3.3.

**R4, the proof.** An untagged image is listed as an RFactory web build only if all three hold:

1. `podman images --filter dangling=true` lists it;
2. its config has the line `RFACTORY_COMMIT=<40 hex characters>`. Only `web/Containerfile:65-69` sets that variable, and `pod.sh` always passes a commit (`deploy/pod.sh:39-41`). The check prints only that one line;
3. `git cat-file -e <that commit>` succeeds in the RFactory checkout.

The removal list shows each such ID with its commit and creation date. That is strong evidence, not certainty: an image that another project built on top of an RFactory image would carry the same line. So the owner names the IDs, and podman gives a second guard: without `-f`, `rmi` refuses an image that has child images or a container. Every other untagged image stays, whatever its size.

**Kept, and checked afterwards:**

- `~/.config/rfactory/` and every file in it, including `scope.json` and its two old copies;
- `~/.config/rfactory-verify/` and `~/.local/share/rfactory/claude-home`;
- the spike profile volumes `rfactory-spike-profile-chrome` and `-chromium`: a rebuild cannot restore a signed-in browser profile;
- the pulled `oauth2-proxy` image (`deploy/pod.sh:18`);
- every untagged image that R4 does not prove, and every image and volume of another project;
- Keycloak client `rfactory`, all its callbacks and web origins;
- everything in the cluster, the registry, Docker and k3d, and the port `127.0.0.1:18443`.

**Never used:** `podman image prune`, `podman system prune`, `podman volume prune`, `rmi -f`, a wildcard, or a name built by a loop over a pattern. The store is shared with other projects.

### 6. What is recorded

- **#37:** the go/no-go comment and the removal list. Then each box is ticked with the exact names removed, or marked `kept`, `refused` or `failed` with the reason. The callback and `scope.json` boxes are marked "kept". No comment holds a secret, a member's address or a file's content.
- **The rollback line in #37 is corrected** to #33's order (`plan/2026-11-24-33-rfactory-in-cluster.md:382-387`):
  1. set `replicas: 0` in factory-gitops and wait for the pod to stop;
  2. run `deploy/pod.sh up` from a clean, pushed checkout;
  3. repoint the hostname or callback as needed.

  Records written in the cluster are not copied back. The comment also says what is weaker after the removals: the images must be rebuilt, and the old records exist only in the cluster PVC and the archive.
- **Follow-up issue A:** how the desktop verify scripts sign in without the `127.0.0.1:4180` callback, including a first start of the local pod after the cleanup. The callback is deleted when it lands, with a bus post first, and every other entry of the client left as it is.
- **Follow-up issue B**, only if a proof build failed: `deploy/pod.sh` cannot rebuild that image.
- **`README.md:11-15`** gets two or three plain sentences: what was removed from p620 and when, whether each proof build passed or failed, that the local pod has not been started since the cleanup, and the follow-up issue numbers. This is the only repository change besides the artifacts.

### 7. Deferred

- Deleting the Keycloak callback (follow-up A).
- Starting the local pod after the cleanup to show a sign-in (follow-up A, Open question 4).
- Untagged STT or spike builds, and the old `scope.json` copies.
- A test of the CFactory write key from the cluster.
- Retiring `deploy/pod.sh`.
- A start of `rfactory-web` that waits for CFactory instead of exiting.

## Alternatives rejected

- **Do what #37 lists as it stands.** It deletes `scope.json` and the callback, which the local pod and the verify scripts still use, and it gives the rollback in the wrong order.
- **`podman image prune` for the untagged layers.** It removes other projects' images from the shared store. The intent forbids it.
- **Prove an untagged image by its size or age.** Other projects build images of the same size. Only the commit line ties an image to this repository.
- **Plain `podman rmi`.** It also removes parents that become dangling, which nobody named.
- **Restart the cluster pod to prove records persist.** It interrupts the live deployment for evidence the PVC already gives: a cluster record older than the running pod.
- **Skip the archive, since the PVC has the records.** The copy is 16K. Without it the deletion depends on one `local-path` volume, and the app prunes that copy after 90 days.
- **Remove the web image without the rebuild proof.** If the pinned Chrome no longer installs, `pod.sh up` would be broken and nobody would know until it was needed.
- **Run the proof builds before 2026-12-01.** A build writes to p620's shared store, and the intent allows only read-only checks until then (Open question 2).
- **Let an agent run the removals unattended.** The owner decided each removal is run in the owner's session after the OK.

## Risks

All on p620 unless stated.

- **A wrong image is removed.** The store is shared. Mitigation: exact names and full IDs only, `--no-prune`, the ID re-check before each command, the R4 proof with the owner naming each ID, no force, and a diff of the lists after.
- **The records are lost.** After R5 they exist in the PVC and the archive only. Mitigation: item 5 and the archive check run first, the sums are read again just before the removal, and the volume goes last.
- **The proof build changes the shared store.** For a while it adds one tagged image of about 2 GB. `--pull=never` and `--layers=false` keep it from pulling a base image or leaving layers behind.
- **Rollback is weaker after the day.** The owner accepts this in the second OK: images must be rebuilt, the Claude login in `claude-home` has no refresh path and goes stale, and a new local volume starts empty.
- **The go/no-go proves less than it seems.** Items 2, 3 and 5 have stated limits. Both comments in #37 repeat them so the OKs are given with them in view.
- **A deploy lands during the day.** Then the owner's test was for another revision. Mitigation: step 7 reads item 1 again; a changed pod UID or revision stops the day.
- **Cluster:** the agent runs `kubectl get` and one `kubectl exec` that lists sums. It writes nothing and reads no Secret. The owner's test call writes one share record, as any call does.
- **Keycloak:** no change, so no risk to the live sign-in.

## Verification

Done is proven on the day, in this order. Each result goes into #37.

1. **The go/no-go comment exists** in #37 with six rows, each `pass` or `fail`, the evidence, the revision checked and the stated limits.
2. **The archive is good:** mode 600, and its file list and SHA-256 sums equal the p620 sums of 3.3.
3. **Each removed item is gone:** `podman image exists` or `podman volume exists` returns 1 for every name and ID marked `removed`.
4. **Nothing else changed.** The after-lists equal the before-lists minus the items marked `removed`. The proof tag was made after the before-lists, so it is tracked on its own: it is gone, or reported as kept. Every tag that stays still points at the same ID. Any other difference is reported to the owner at once.
5. **The kept things are there:** `scope.json` with mode 600, the `claude-home` directory, `~/.config/rfactory-verify/`, both spike profile volumes, and the `oauth2-proxy` image.
6. **The cluster still answers:** an unauthenticated `GET https://rfactory.freundcloud.org.uk/` returns 302 to Keycloak, item 1 of the go/no-go still passes with the same PVC, and the owner reloads the signed-in page and sees it.
7. **The record is complete:** every #37 box is ticked or marked, the rollback line is corrected, follow-up A is open (and B if a proof failed), and no comment holds a secret or an address.
8. **The repository:** the README change is the only change besides the artifacts; `git diff --stat` shows it.

Each live check is one run. A failed check is investigated before any second run.

## Open questions

1. **Is there a source for restarts of earlier pods?** Recommendation: the plan checks once, read-only, whether the cluster keeps restart metrics. If it does, item 3 uses them. If not, the owner attests that part, as the intent allows.
2. **May the proof builds run before 2026-12-01?** An early run would let a `pod.sh` fix land before cleanup day. But a build is not a read-only check, so it would relax the approved intent. Recommendation: no. Run them on the day, after the first OK. If the web proof fails, the web image and the untagged web builds simply stay until follow-up B lands.
3. **Where does the archive go?** Recommendation: `~/.local/share/rfactory/rfactory-actions-p620-2026-11-24.tar`, mode 600. That directory stays, and `pod.sh` does not read the file.
4. **Start the local pod after the cleanup to prove a sign-in?** A normal `pod.sh up` would run a second instance against the live CFactory and desktop runner, which #33 forbids. Recommendation: no. The proof builds and the README note are the known state; a real start belongs to follow-up A.
5. **Remove the rebuild-proof image when the proof passes?** Recommendation: yes. `pod.sh up` rebuilds on demand, and the issue's aim is to free the space.
6. **Keep the untagged web builds (R4) in this slice?** They are most of the disk space, but they are the one removal that rests on evidence and not on a name. Recommendation: keep R4, with the three-part proof and the owner naming each ID. Leaving it out is the smaller option: then only named images and the volume go.
