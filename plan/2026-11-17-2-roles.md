# Plan: v1 roles in code (admin, approver, member), slice "roles" of #2

Self-contained. Builds #2's approved **v1 roles, per scope** (spec
"Scopes, roles, credentials", a shared rule approved with the spec) as code,
so #3 step 13 (desktop handover, share approval, profile admin) can call one
role check. It adds no new permission: today the deployment already has two
role lists in the environment, and this plan names them, adds the admin
list, and routes every check through one module.

## Decisions carried over from the approved spec

| Role | May |
|---|---|
| admin | connect sources, approve brains, enable writes |
| approver | approve the changes in the queue |
| member | start a bot, view calls and status |

- Roles are **per scope**. A deployment runs one scope today (the scope
  file), so the role lists belong to that scope.
- Read access to a scope's content follows the roles.
- An approver must also pass the source authority check for each write;
  that check is #2 S6 (GitHub/GitLab writes) and is **not** in this plan.
  CFactory writes (#10) keep their existing checks unchanged.

## Decisions for this plan

- **Where the lists live:** the environment, as today (no database yet; the
  spec's database store comes with the first multi-scope slice):
  - `RFACTORY_ALLOWED_EMAILS`: members (unchanged meaning);
  - `RFACTORY_APPROVERS`: approvers (unchanged meaning);
  - `RFACTORY_ADMINS`: admins (new, optional; empty means no one can do
    admin-only actions, which today are none in `main`; #3 step 13 uses it
    for desktop profiles and approved previews).
- **Implications:** every approver and every admin must also be a member;
  otherwise the server refuses to start (`roles-not-members`), because an
  approver who cannot open the page is a misconfiguration, not a silent
  downgrade. Admin does not imply approver (the spec lists different
  powers; the owner is put in both lists).
- **Normalisation:** trimmed, lower-cased, empty entries dropped, duplicates
  removed; an entry that is not `local@domain` refuses start
  (`roles-invalid-email`).
- **One check:** `core/src/roles.js` exports `loadRoles(env)` →
  `{ has(email, role), rolesOf(email), approvers }`, frozen; `has` is
  case-insensitive and false for a missing email. `role` outside
  `admin | approver | member` throws (a typo must not read as "no").
- **Scope file:** unchanged; no role fields in it in this slice.

## Steps

1. **`core/src/roles.js`, `core/test/roles.test.js`** (new).
   `loadRoles(env)` as decided above.
   → verify: `(cd core && npm test)`: lists parsed and normalised; an
   approver or admin not in members → throws `roles-not-members`; a bad
   entry → `roles-invalid-email`; `has()` is case-insensitive, false for
   `undefined`/empty email, throws on an unknown role; `RFACTORY_ADMINS`
   unset → no admins; returned object is frozen; a **role matrix** (outsider,
   member only, member + admin, member + approver, all three) gives exactly
   the expected `has()` answers, in particular admin without approver is
   not an approver.
   Traps: pure module, no I/O; never log the lists' contents at error
   (the error code only).
2. **`web/server.js`, `web/actions.js`, `web/test/server.test.js`,
   `web/test/actions.test.js`.** `main()` builds `roles = loadRoles(process.env)`
   once and passes it to `createApp({ roles, … })` and
   `createActionManager({ roles, … })` in place of `allowedEmails` and
   `approvers`. The member check (`403 forbidden`) becomes
   `roles.has(email, 'member')`; `can_approve` and the action manager's
   approver checks on **both approve and reject** (`web/actions.js` 94 and
   167) become `roles.has(email, 'approver')`. Behaviour is unchanged for
   existing deployments.
   → verify: `(cd web && npm test)`; existing tests keep their assertions,
   built with a `loadRoles` fixture; new tests: an approver missing from
   members makes `main()`'s role load throw before listening; an admin who
   is not an approver gets `can_approve: false` and is refused on approve
   and on reject.
   Traps: `#13` (PR #14) also edits `web/server.js` `createApp`'s options
   (`commit`) and `main()` (voices); whichever merges second rebases;
   keep both.
3. **`deploy/pod.sh`, `web/test/pod.test.js` (new), `README.md`.** Today
   `RFACTORY_APPROVERS` reaches the container only inside the write-key
   branch, so with writes off or no write key the approvers silently
   vanish (Codex review of this draft). Forward `RFACTORY_APPROVERS` and
   `RFACTORY_ADMINS` whenever set, independent of the write settings; keep
   the existing rule that writes on require `RFACTORY_APPROVERS`. Document
   the three lists and the "approvers and admins must be members" rule.
   → verify: `shellcheck deploy/*.sh`; `web/test/pod.test.js` runs
   `pod.sh up` with a fake `podman` (and fake config files under a temp
   `RFACTORY_CONFIG`) on `PATH` and checks the `podman run` arguments for
   rfactory-web in three cases: writes off with approvers set → approvers
   passed; no write key with approvers and admins set → both passed; write
   key present without `RFACTORY_APPROVERS` → refused as today.
   Traps: no secrets involved; the lists are e-mail addresses, keep them
   out of logs.
