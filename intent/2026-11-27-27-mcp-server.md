# Intent: an MCP server for agents, slice A: read RFactory with a read key

## Problem

Issue #27 (2026-11-21) asks for an MCP server so agents (Claude Code, CFactory) can manage RFactory and review its work. Before this draft it had no intent, spec, plan or PR. Its sibling #26 (CLI) has a draft intent on its own branch (`intent/2026-11-26-26-cli-control.md`); the two must share one control API.

1. **An agent has no way in.**
   - **The server:** it listens on 127.0.0.1 only (`web/server.js:434`) and accepts a request only when it carries `X-Forwarded-Email` for a listed member (`:161-163`). The live-view socket follows the same rule (`web/live-view.js:51-53`).
   - **The login:** oauth2-proxy sets that header from a person's browser sign-in (`deploy/oauth2-proxy.yaml:24-28`). #33 decided "no bearer-token pass-through" (`spec/2026-11-24-33-rfactory-in-cluster.md:68`).
   - **The roles:** member, approver and admin are lists of email addresses (`core/src/roles.js:10-12`). There is no agent identity, no key and no read or write scope.
2. **The MCP endpoint that exists is not for outside agents.** `core/src/lookup-endpoint.js` serves the bot's own brain: a random port on 127.0.0.1 (`:43`), a random token per turn (`:47`), read-only lookups, at most 8 calls (`:33`). Nothing outside the pod can use it, and it must stay that way.
3. **Part of the issue's list has no API behind it.**
   - **"List calls":** there is one call slot (`/api/call/status`, `web/server.js:263`). No call history is kept.
   - **"Read transcripts":** call content is discarded after the call (#28: `intent/2026-11-23-28-factory-review-control.md:138`). Only the running call's live event stream exists (`web/server.js:299`).
   - **"Read the action record":** the record is daily files on disk, kept 90 days (`web/actions-record.js:7`, `:9-20`). It is read only to recover after a restart (`:60-66`); no route returns it. The page's list (`/api/actions`, `web/server.js:207`) is the server's memory, which is emptied when the next call that can propose starts (`web/actions.js:179-185`, `web/call.js:592`).
   - **"Propose actions":** a proposal is made only by voice in a running call. The action manager refuses without one (`web/actions.js:49`), turns free text into an action through the brain (`:53`), and records the proposer as a spoken name, not an identity (`:77`). No HTTP route proposes anything.
   - **"Read investigation state and reports":** this exists (`/api/investigations`, `web/server.js:223`; the entry carries the report and test results, `web/investigations.js:55-66`). Only the newest report is kept (`:100`).
   - **"List scopes":** the issue does not say whether this means the projects, or what the caller may do (decision 8).
4. **"Manage" is not defined.** The issue's examples are reads and proposals. Whether an agent may also join or leave a meeting is not said (decision 7).
5. **Today's reads assume a member who may see everything.**
   - Status names the running call's project to any member (`web/server.js:263-264`).
   - The record mixes projects: lookup lines carry a project (`web/call.js:228-230`), action and investigation lines carry none (`web/actions.js:75-78`, `web/investigations.js:273-276`).
   - The review route passes card text, comments and stage detail on without a redaction step of its own (`web/server.js:172-185`), and stage results can come from another card (`core/src/review.js:9`, CFactory#583).
   - So "the same as the page" is not yet a safe rule for an agent that is limited to some projects and sends what it reads to a model provider.

## Proposed outcome

One MCP server through which an agent reads RFactory with a read key. Slice A is read-only. It covers project-aware deployments (#52), which is what runs today, as #26's slice A does.

- **Agent keys.** An agent connects with its own key. A key has a name (which agent), a scope (`read` in this slice) and the projects it may see. A missing, wrong or revoked key gets nothing.
- **Reads, as tools:**
  - **What this key may do:** its name, scope and projects.
  - **Status:** is a call running or starting, plus the server's commit (`/api/call/status`, `/api/config`; `web/server.js:187`, `:263`). The project is named only when the key may see it; otherwise the answer is "busy" (decision 3).
  - **Projects:** the projects the key may see (`/api/projects`, `:167`).
  - **Standup,** per project, and **review,** per project and per card (`:172-185`, `:193-199`).
  - **Actions, shares and investigations,** per project: what is pending and past, what is running for shares and investigations, and an investigation's report and test results (`:207`, `:223`). An agent sees `can_approve: false`, always.
  - **The action record** (decision 4): the kept 90 days, only lines that belong to a project the key may see. Old lines that carry no project are left out.
- **No tool changes anything.** The server offers an agent no approve, reject, stop, join, leave or propose tool, and refuses those for every agent key, whatever its scope.
- **One control API.** The page, the CLI (#26) and this server use the same read logic. What each caller may see, and how it is made safe for that caller, is decided per caller. A check added to the shared logic applies to all.
- **Attributable.** Every agent call is logged with the key's name, the tool and the project, and never its content or the key.

**Not in slice A:** the state of an elevated-call grant (#22 is a draft; a read of it is added when #22 exists, under the same project rule).

**Later slices, each with its own intent:**

- **B: propose.** A key with the `propose` scope may propose an action or an investigation. A signed-in approver still approves each one on the page (#10, #22). This needs new server routes, the same ones as #26's slice C (decision 6).
- **C:** a call history, and kept transcripts (decision 5).

## Affected users and systems

- **Agents:** Claude Code on the owner's machines, and CFactory in the cluster. Each gets its own key.
- **Admins:** they issue and revoke keys, as a deployment change (decision 1).
- **Members and approvers:** nothing changes for them. Approving stays on the page.
- **`web/` and `core/`:** the shared read logic, the agent entry and its key check, the MCP tools, and a read of the record. `@modelcontextprotocol/sdk` is already a dependency (`core/package.json:8`). The spec places the code.
- **The way in** (decision 2): inside the cluster and the owner's private network only, not the public hostname. Affected: oauth2-proxy (`deploy/oauth2-proxy.yaml`), the Service and the tunnel. The live Service, tunnel and proxy settings are in `factory-gitops` (#33; `spec/2026-11-24-33-rfactory-in-cluster.md:54-68`). DNS and Keycloak clients are in no repository (`:56-57`).
- **`core/src/lookup-endpoint.js`:** unchanged (decision 9).
- **#26 (CLI):** shares the read logic now, and the propose routes later. It does not share the sign-in: a person signs in, an agent holds a key. Whether a signed-in person may approve from the CLI is #26's own question; nothing here assumes it.
- **#22 (elevated calls):** pairing, approving and revoking stay with the signed-in person on the page.
- **#25 (user guide):** how to connect an agent.

## Constraints

- **An agent never approves.** No key, scope or tool lets an agent approve, reject, stop, pair or revoke. Those need a signed-in person on the page (#10, #22, #28). The server enforces this; the tool list is not the boundary.
- **An agent is never taken for a person, on any way in.**
  - An agent's credential is never accepted where a person's sign-in is expected: not by the proxy, not by the page routes, not by the live-view socket. This holds for every kind of credential, including a token from the identity provider.
  - The agent entry never accepts an email header, and a key never holds the member, approver or admin role.
  - The page routes stay reachable only through the proxy, whatever is opened for agents.
  - The spec proves each of these live, including a client-sent `X-Forwarded-Email` on the agent's path.
- **Read and write scopes are split** (#27). A `read` key can never propose. In this slice no other scope exists.
- **Keys are secrets:**
  - the key itself is never in Git, a URL, the environment, a log, the record, an error message or a tool answer (today's environment check covers only CFactory's key names, `web/server.js:329-331`);
  - it travels only over an encrypted connection;
  - one key can be revoked without touching the others, and a revoked key stops working within a time the owner sets (decision 1), also for a connection that is already open.
- **Projects, checked per item:**
  - an agent sees only projects that are in the deployment's allowlist and in its key's list, and a project is checked against both before CFactory is asked for it, as `bind` does today (`web/server.js:104-105`);
  - every list entry and record line is given only when it belongs to such a project. A line that cannot be tied to a project is not given to an agent (decision 4);
  - an agent learns nothing about another project's call beyond what decision 3 allows.
- **What an agent gets must be safe for a model provider.** Page parity is not enough (problem 5). Every tool answer, including errors, old record lines and fields of uncertain origin, is redacted for that destination. No RFactory or CFactory credential ever reaches an agent.
- **An agent is a new destination for Factory data.** What a tool returns goes to the agent's model provider. The owner decides which agent gets a key, and for which projects.
- **Call content:** the live stream is not given in slice A. Text that came from a call and is kept, such as an investigation's spoken request and the proposer's name (`web/investigations.js:273-275`), follows decision 3.
- **Untrusted both ways.** Card text, reports and logs an agent reads are data, and the tools say so. Nothing an agent sends is trusted: every argument is validated as the routes validate today (for example the card key, `web/server.js:180`).
- **Agents must not get in the page's way.** Agent reads are limited, and never make the page answer "busy" (today one standup read runs at a time for the whole server, `web/server.js:193-198`).
- **Retention is unchanged.** The server keeps nothing new. The record stays at 90 days.
- **Self-hosted only.** No hosted service, no new paid dependency, and no new npm dependency unless the spec shows the need.
- **Deploying:** a proxy, Service or tunnel change goes through `factory-gitops`; secrets stay out of Git, as #33 requires. Builds and deploys need the owner's OK and an announcement on the agent bus first.

## Decisions (2026-11-27)

The owner approved with the recommended answers ("use recommendations and approve"):

1. **Agent keys:** one secret per agent, set up with the deployment, as the CFactory keys are (a mounted file, the value never in Git). The scope and project list sit in the deployment's configuration. An admin issues and revokes a key by a deployment change. A revoked key stops working at the latest with that change: minutes, not seconds. The spec still verifies how CFactory's scoped keys are built.
2. **Reach:** inside the cluster and the owner's private network only. Not on the public hostname.
3. **Calls:**
   - another project's call: an agent learns only that the slot is busy;
   - live call content: not given in slice A;
   - kept text that came from a call: an investigation's spoken request is given; the proposer's spoken name is left out.
4. **The 90-day action record is in slice A,** through a new read that the page and the CLI can use too. Old action and investigation lines that carry no project are left out for agents, unless the owner later confirms that every one of them came from the default repository.
5. **Call history and transcripts:** not now. A call history without content is decided later, together with #26's question 10. Kept transcripts would change #28's retention rule and are not planned.
6. **Proposing without a running call:** no for now; a proposal stays inside a call. Slice B's intent may reopen this. *(No recommendation was given; lead's default, owner may revisit.)*
7. **Join and leave:** an agent may not join or leave a meeting.
8. **"List scopes"** means the key's own name, scope and project list.
9. **Read-only is the first slice.** Proposing follows as slice B, with #26's slice C. *(No recommendation was given; lead's default, owner may revisit.)*
10. **The bot's own tools (#51)** stay on the lookup endpoint. They do not go through this server.
11. **Agent reads** go in the log only, not in the 90-day record.
