# Intent: a command-line tool for RFactory, slice A: sign in, read, join and leave

## Problem

Issue #26 (2026-11-21) asks for a command-line tool to control and automate RFactory. Before this draft it had no intent, spec, plan or PR.

1. **Today's CLI can't control the running service.** `core/bin/rfactory-standup.js` has three commands (`approve-destination`, `standup`, `ask`, `:15`). It reads a scope file and talks to the source and the brain itself (`:29-56`). It never talks to the web server, so it can't see or change a call, an approval or an investigation.
2. **The web server has no sign-in for a program.**
   - **The login:** the checked-in deployment offers a browser sign-in only. oauth2-proxy sits in front and sets `X-Forwarded-Email` from the verified sign-in (`deploy/oauth2-proxy.yaml:24-28`).
   - **The server:** it listens on 127.0.0.1 only (`web/server.js:434`) and trusts that header (`:161-163`).
   - **The result:** no documented way exists for a command-line tool to sign in.
3. **Every call needs a person at the page.** Joining, leaving, checking status and reading what the bot heard all need the browser. So none of it can be scripted, for example "join the 09:00 standup" from a timer, or a status check from a terminal.
4. **Part of the issue's list has no API behind it yet:**
   - **"List calls":** there is one call slot, and no call history is kept (#28: call content is discarded after the call).
   - **"Start an investigation":** this happens only by voice in a call. `core/src/call/hearing.js:15` recognises the request and `web/call.js:368` makes it. No HTTP route proposes one.
   - **"Show what the bot heard":** this exists only as the live event stream of the running call (`web/server.js:299`).

## Proposed outcome

One command-line tool that talks to the same HTTP API as the page, signed in as a person. Slice A covers signing in, every read, and join and leave. It covers project-aware deployments (the scope lists projects, #52), which is what runs today (question 7).

- **Sign in and out.** A person signs in on their own machine. Every later command acts as that person, with that person's role (member, approver, admin; `core/src/roles.js`). Signing out removes the sign-in from that machine.
- **Reads,** all on routes that exist today:
  - **Status:** is a call running or starting, for which project, plus the server's commit (`/api/call/status`, `/api/config`; `web/server.js:187`, `:263`).
  - **Projects:** the projects this deployment allows (`/api/projects`, `:167`).
  - **Standup and review,** per project: the same data as the page (`/api/standup`, `/api/review`; `:172-193`).
  - **Actions, shares and investigations,** per project: what is pending, running and past (`:207`, `:223`). A project without the default repository shows empty lists, as on the page.
  - **Heard:** follow the running call's events for its project, which are questions, answers, state and hearing mode (`/api/call/events`, `:299`). It ends when the call ends. It shows events from the moment it starts; earlier questions and answers are not replayed.
- **Call control:**
  - **Join** a meeting link for a project, with an optional listening mode (`POST /api/call`, `:267`).
  - **Leave** the call that the person just saw in status (`DELETE /api/call`, `:287`). The server refuses if another call has started since (the generation check, `:293`).
- **Good for scripts:** machine-readable output, and failures a script can tell apart (not signed in or not allowed, refused by the server, anything else). The spec fixes the exact form.
- **The server stays the judge.** The tool adds no power: every check (role, project allowlist, busy, generation) is made by the server, as for the page.
- **The old commands keep working.** `rfactory-standup`'s three commands behave as today (the bench harness and its tests use them: `core/bench/ollama-standup.js:5`, `core/test/cli.test.js:12`).

**Later slices, each with its own intent:**

- **B:** approve, reject and stop from the CLI (question 2).
- **C:** start an investigation or propose an action from the CLI. This needs new server routes; #27 (MCP server) needs the same ones.
- **D:** anything that needs a call history ("list calls").

## Affected users and systems

- **Members, approvers and admins:** they get a second way in. Their roles and limits don't change.
- **`core/bin/`:** the new commands and their tests. They hold no scope file.
- **The sign-in path** (question 1):
  - **oauth2-proxy:** `deploy/oauth2-proxy.yaml`; the local pod pins v7.7.0 and passes no setting for non-browser sign-in (`deploy/pod.sh:18`, `:137-144`).
  - **The identity provider:** Keycloak, client `rfactory`.
  - **The live cluster settings:** they live in the `factory-gitops` repository, not here (#33; `spec/2026-11-24-33-rfactory-in-cluster.md:52`). `deploy/k8s/` holds only the desktop infrastructure.
- **`web/server.js`:** possibly nothing. None of slice A's routes checks the `x-rfactory-action` header or the request's origin; only approve, reject and stop do (`:69-72`, `:208-211`, `:229`). The spec confirms this.
- **#27 (MCP server):** it shares the API. It does not have to share the sign-in: #27 asks for split read and write keys for agents, and an agent may only propose.
- **#25 (user guide):** the CLI needs a page there, or a section in the README.

## Constraints

- **No new powers.** The CLI can do only what the same person can do on the page (#26).
- **No way around the login.** The tool never talks to the server behind the proxy, and it never sends an email address of its own choosing. A person's identity comes only from the identity provider. The proxy stays the only way in (#33).
- **Secrets:**
  - the sign-in is kept on the person's machine, readable only by that person;
  - it is never printed, logged or passed on a command line;
  - the web client's secret is never given to the CLI;
  - the server's redaction of what it returns is unchanged.
- **Approvals stay on the page in slice A.** #28's rule ("every write is approved on the signed-in web page", which includes stopping Factory work) holds until the owner decides question 2. Leaving a meeting is not such a write: the page's Leave needs no approval today.
- **If slice B comes,** it keeps every approval rule of #10 and #28: approvers only, the exact action and effects as the server describes them, expiry, fresh scope checks, at most one run, the action record, and no retry after an uncertain result.
- **Untrusted input stays untrusted.** Text the CLI prints (card text, captions, answers) is data. The tool never runs it, and it must not let that text control the terminal (escape sequences).
- **Retention.** The tool keeps nothing itself: call content is discarded after the call (#28). What a person saves from its output is theirs to handle (question 5).
- **Projects** are named by the deployment's allowlist, and a call stays bound to the project it started with (#52).
- **One call at a time,** as today. Joining on a busy server fails with the server's own "busy".
- **Self-hosted only.** No hosted service and no new paid dependency.
- **Deploying:** a proxy or identity-provider change goes through `factory-gitops`. Builds and deploys need the owner's OK and an announcement on the agent bus first.
- **No new dependencies** unless the spec shows that Node's standard library and `core/`'s two existing ones (`core/package.json:7-10`) can't do it.

## Decisions (2026-11-27)

The owner approved this intent with its recommendations. "(default)" marks an answer where no recommendation was given: lead's default, owner may revisit.

1. **(a)** Device sign-in. The spec must still check the live proxy and Keycloak settings, versions and token contents before anything is built.
2. **(a)** Approve, reject and stop are slice B, with its own intent, after slice A's sign-in has been in use. It would change #28's rule to "on the signed-in page or the signed-in CLI". Slice A only lists them.
3. **Unattended use is not in slice A.** A person signs in, and the sign-in lasts as long as the provider allows.
4. **Removing the sign-in from the machine is enough** for signing out.
5. **Yes,** `heard` may print call content to the terminal. It is the same content the page shows a member.
6. **A new `rfactory` command** next to the old tool, which is left alone.
7. **Deployments without projects are left out of slice A.**
8. **The CLI must name the project** for Leave, as the page does. The server's call counter restart across a server restart is accepted, as on the page.
9. **Join succeeds when the server accepts the request,** as on the page, with `heard` or status to follow.
10. **Status and projects are enough for now.** No call history, so call content is still discarded after the call.
11. **Slice A is the first slice** (default; no recommendation was given; the full control API with #27 comes after).
